# Baseline, блок 10 (20.11.2026)

> **Поправка из блока 11.** Просмотр каталога и обычные брони здесь сняты через несколько минут после старта, на холодных JVM. «Gateway добавляет 300 мс» — это JIT-прогрев, на прогретом стеке каталог держит 400 rps с p99 40–72 мс. Тесный bulkhead платёжки подтвердился. Сравнение на прогретых сервисах — в [before-after.md](before-after.md).

Первые цифры до оптимизаций блока 11. Всё на одном ноутбуке: 12 логических ядер, все сервисы и инфраструктура в Docker (`--profile apps --profile obs`), лимит памяти сервиса 512 МБ, k6 на той же машине. Сервисы прогреты.

## Просмотр каталога

`k6 run load/catalog-browse.js` — 100 итераций в секунду, 60 с. В итерации 4 запроса: лента города, поиск с опечаткой, карточка события, заполненность зала.

| Запрос | p50 | p95 | p99 |
|---|---|---|---|
| Лента города | 350 мс | 1.13 с | 1.41 с |
| Поиск | 339 мс | 1.09 с | 1.38 с |
| Карточка события | 292 мс | 1.09 с | 1.55 с |
| Заполненность зала | 248 мс | 984 мс | 1.25 с |

371 запрос в секунду, ошибок 0. k6 не удержал заданный темп: 433 итерации пропущены (нужно было 400 запросов в секунду).

**Где время** (серверная сторона, Prometheus за то же окно):

| Сервис | p50 | p99 |
|---|---|---|
| api-gateway | 362 мс | 1.40 с |
| catalog-service | 38 мс | 447 мс |
| booking-service | 25 мс | 271 мс |

Gateway добавляет около 300 мс к медиане при 2.3 ядрах CPU на 390 запросов в секунду. Это первый кандидат в узкие места для блока 11. Под подозрением rate limiter (Lua-скрипт в Redis на каждый запрос, на `POST /bookings` два) и настройки пула Netty.

## Обычные брони

`k6 run load/bookings.js` — 20 покупателей в секунду, 60 с: бронь одного места события 1, оплата, отмена. Платёжка отвечает за 0.5 с.

| Запрос | p50 | p95 | p99 |
|---|---|---|---|
| Бронь | 23 мс | 186 мс | 775 мс |
| Оплата | 539 мс | 605 мс | 2.84 с |
| Отмена | 16 мс | 68 мс | 515 мс |

Оплачено 808 броней из примерно 1200. 157 оплат получили `503`:
- `Bulkhead 'payment' is full` — 42. Bulkhead на 20 одновременных вызовов без ожидания тесен: по закону Литтла 20 оплат в секунду × 0.5 с = 10 вызовов в среднем, всплески выходят за 20.
- Bulkhead общий для оплат и возвратов: 61 возврат после неудачной оплаты тоже получил отказ и прошёл позже через уборщик.
- Circuit breaker открылся один раз на 10 с (виден на дашборде), 21 оплата получила `CallNotPermitted`, остальные — быстрый отказ до вызова. Отказы bulkhead'а breaker не считает. Его открыли таймауты 2 с во всплеске: p99 оплаты 2.84 с — это таймаут, пауза 200 мс и вторая попытка. Retry скрыл первые попытки, в логе их нет.
- 118 отмен получили `409`: бронь уже отменила компенсация после неудачной оплаты, это ожидаемо.

Вывод для блока 11: платёжка под 20 оплатами в секунду иногда отвечает дольше 2 с. Bulkhead без запаса на всплески и общий с возвратами. Нужно разобраться, почему платёжка тормозит, и разделить bulkhead.

## Flash sale

| Запрос | p50 | p95 | p99 |
|---|---|---|---|
| Вход в очередь | 195 мс | 452 мс | 676 мс |
| Статус в очереди | 104 мс | 275 мс | 412 мс |
| Бронь | 213 мс | 739 мс | 1.17 с |

- Броней 9984, конфликтов мест 1045, отказов backpressure (`503`) 447, сдались после 3 попыток 16, `403` 0.
- **Двойных продаж 0** (проверка по `booking_seats` активных броней).
- 798 запросов в секунду, весь прогон 1 мин 41 с.

## Как повторить

```bash
docker compose --profile apps --profile obs up -d --build --wait
k6 run load/catalog-browse.js
k6 run load/bookings.js
k6 run -e USERS=10000 -e USERS_PER_VU=50 load/flash-sale.js
```

Графики во время прогона: Grafana `localhost:3000`, дашборд «Booking platform».
