## Что нашли и что сделали

### 1. «Gateway добавляет 300 мс» — это холодный JVM, а не gateway

Baseline показал p50 gateway 362 мс при 38 мс у каталога за ним. Проверка одним маршрутом (`GET /events/1`, 400 rps):

| | p50 | p99 |
|---|---|---|
| Gateway через минуту после старта | 33 мс | 4.87 с |
| Каталог напрямую | 3 мс | 30 мс |
| Копия gateway без rate limiter'а | 4–5 мс | 18–59 мс |
| Тот же gateway с rate limiter'ом, через несколько минут | 6 мс | 41 мс |

Первые десятки тысяч запросов JVM интерпретирует байткод и компилирует горячие методы (JIT). Пока это идёт, хвосты в десятки раз больше. Повторный прогон каталога без единой правки: p99 1.4 с → 40–72 мс, 400 rps без пропусков. Rate limiter стоит около 0.1 мс на запрос (`EVALSHA` в Redis, 103 мкс по `INFO commandstats`).

**Вывод:** gateway узким местом не был (P30 закрыт). Сравнивать можно только прогретые прогоны. Для HPA в блоке 12 это значит: новая реплика первые секунды отвечает медленно, это стоит учитывать в readiness и масштабировании.

### 2. Bulkhead платёжки ограничивал поток оплат

При 50 и при 100 покупателях в секунду подтверждалось одинаково, около 30 броней в секунду. Остальные оплаты получали `BulkheadFullException` и уходили в компенсацию. Сама платёжка была здорова (p50 0.5 с, p99 0.62 с).

Закон Литтла: одновременных вызовов = поток × время ответа. Bulkhead на 20 при ответе 0.55 с пропускает не больше 20 / 0.55 ≈ 36 оплат в секунду. К тому же bulkhead был общий с возвратами, и всплеск компенсаций занимал места оплат.

**Сделали:** bulkhead оплат 100 (хватит на 100 оплат в секунду с запасом ×2), у возвратов свой на 20. Защита осталась: если платёжка замедлится до таймаута 2 с, через неё пройдёт не больше 50 оплат в секунду, остальные получат быстрый отказ.

### 3. Куча 75% не оставляла места остальной памяти JVM

Под нагрузкой 100/с booking-service занимал 492 из 512 МБ, cgroup упирался в лимит 1682 раза за прогон (`memory.events: max`). Каждый раз ядро притормаживает процесс, освобождая память, отсюда хвосты в секунды. Каталог — 223 раза.

| booking-service под нагрузкой | МБ |
|---|---|
| Куча, выделено (используется ~150) | 241 |
| Не-heap: metaspace, code cache, буферы | 259 |
| Лимит контейнера | 512 |
| Потолок кучи при `MaxRAMPercentage=75` | 384 |

Куча могла вырасти до 384 МБ, а вместе с не-heap это 640 МБ при лимите 512. **Сделали:** `MaxRAMPercentage=50` для всех сервисов, booking и catalog получили 768 МБ (+512 МБ к бюджету). После: 0 упираний в лимит.

### 4. Что проверили и что не помогло

| Гипотеза | Эксперимент | Результат |
|---|---|---|
| Мало соединений в пуле Hikari (20 заняты, до 174 ждут) | Пул 40 | 67 подтверждений/с против 68, p99 брони 1.68 с против 1.1 с. Хуже |
| Медленный fsync на COMMIT (ожидания `WALWrite`, `WalSync`) | `synchronous_commit = off` на время замера | 65/с, без изменений |
| Outbox не успевает | Размер таблицы outbox под нагрузкой | До 252 строк, разбирается за секунду |
| Виртуальные потоки прилипают к носителю (`synchronized`, Java 21) | JFR, `jdk.VirtualThreadPinned` | 0 событий |
| Полные сканы в MongoDB | `serverStatus`, индексы | Индексы есть, 2 скана за всё время |

Почему не помог пул: Postgres показывал в основном `idle in transaction` (соединение занято, а приложение не шлёт запрос), а ответы JDBC приходили через ~20 мс. Load average Docker-VM 15–18 при 12 ядрах: процессы стоят в очереди за CPU. Больший пул — больше одновременных транзакций на тот же CPU, хвосты только растут. Пул остался 20.

## Где теперь предел

Около 77 оплаченных броней в секунду (230 HTTP-запросов в секунду на пути брони), и упирается в CPU ноутбука. booking-service — 3.3 ядра, Postgres — 1.5, MongoDB — до 1.3, gateway и notification — по 0.9. Профиль CPU booking-service ровный: Spring MVC, Hibernate и Spring Data без одной горячей точки. Следующий шаг — горизонтальное масштабирование (блок 12), а не правка одного места.

## Как повторить

```bash
docker compose --profile apps --profile obs up -d --build --wait
k6 run -e RATE=60 -e DURATION=40s load/bookings.js     # прогрев
k6 run -e RATE=100 load/bookings.js
k6 run -e USERS=10000 -e USERS_PER_VU=50 load/flash-sale.js   # на зале без чужих холдов
k6 run load/catalog-browse.js
```

Flash sale берёт места подряд от первого свободного. После предыдущего прогона нужно подождать 10 минут, пока истекут холды, иначе почти все брони получат 409.
