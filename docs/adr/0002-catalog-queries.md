# ADR 0002: каталог событий — индексы, пагинация, N+1

**Статус:** принято, 25.10.2026 (блок 5)

## Контекст

События переехали из booking-service в отдельный `catalog-service` со своей базой `catalog`. Каталог читают на порядки чаще, чем бронируют: лента «что идёт в городе», карточка события. Данных много: 100 000 событий, 200 площадок, 5 000 артистов, 200 000 связей событие–артист.

Нужно, чтобы:
- лента отвечала за единицы миллисекунд на любой странице, а не только на первой;
- страница из 20 событий с площадкой и артистами не превращалась в 41 SQL-запрос;
- бронирование проверяло событие в каталоге и не держало при этом соединение с БД.

## Решения

### 1. Частичные индексы под ленту

```sql
CREATE INDEX idx_events_on_sale_city ON events (city, starts_at, id) WHERE status = 'ON_SALE';
CREATE INDEX idx_events_on_sale      ON events (starts_at, id)       WHERE status = 'ON_SALE';
```

- Порядок колонок повторяет запрос: равенство по `city`, затем сортировка `starts_at, id`. Индекс отдаёт строки уже отсортированными, в плане нет `Sort`.
- `WHERE status = 'ON_SALE'`: черновики и распроданные (20%) в индекс не попадают.
- `city` скопирован из `venues` в `events` (денормализация). Иначе фильтр по городу шёл бы через JOIN, и одним индексом «город + дата» было бы не обойтись.
- Статус в JPQL записан литералом, а не параметром: частичный индекс применим, только если планировщик видит `status = 'ON_SALE'` в тексте запроса. Проверено по SQL, который генерирует Hibernate.

### 2. Keyset-пагинация вместо OFFSET

`WHERE (starts_at, id) > (:startsAt, :id) ORDER BY starts_at, id LIMIT 21`. Курсор клиенту отдаётся непрозрачной строкой (base64 от `startsAt|id`), мусорный курсор даёт 400. Запрашиваем на одну строку больше, чтобы без `count(*)` понять, есть ли следующая страница.

### 3. N+1: JOIN FETCH для площадки, пачка для артистов

- Площадка (`@ManyToOne`) приходит тем же запросом через `join fetch e.venue`.
- Артистов (`@ManyToMany`) fetch-join'ом не грузим: вместе с `LIMIT` Hibernate выполнил бы его в памяти (HHH90003004). Их догружает `default_batch_fetch_size: 50` одним запросом `WHERE event_id = any(?)`.
- Карточка события: `@EntityGraph(attributePaths = {"venue", "performers"})`, один запрос.
- В booking-service тот же `default_batch_fetch_size` закрыл P4: места брони грузятся одним IN-запросом.

### 4. booking-service → catalog-service

`RestClient` с таймаутом 2 с на соединение и чтение. Каталог спрашиваем до транзакции, через `TransactionTemplate`, иначе медленный каталог держал бы соединения из пула на 20. Ответы:
- 404 каталога даёт 404 `EventNotFound`;
- 5xx, таймаут или отказ соединения дают 503 `CatalogUnavailable`.

Одновременные запросы про одно событие склеиваются в один HTTP-вызов (single-flight), ответ живёт в памяти 5 секунд, ошибки не кэшируются.

## Замеры

PostgreSQL 17 в Docker, 100 003 события, `EXPLAIN (ANALYZE, BUFFERS)`.

| Запрос | Без индексов | С индексами |
|---|---|---|
| Лента города, первая страница | Seq Scan 100 000 строк + Sort, **22.8 мс**, 1 259 буферов | Index Scan 21 строки, **1.1 мс**, 44 буфера |
| Страница 3 000 через keyset | Seq Scan + Sort, 27.6 мс | Index Scan 21 строки, **0.7 мс** |
| Страница 3 000 через `OFFSET 60000` | — | Index Scan **60 021 строки**, **87 мс**, 60 687 буферов |

Результаты keyset и OFFSET на одной и той же странице совпадают.

- OFFSET с индексом всё равно читает все пропущенные строки: 60 000 прочитать, чтобы выбросить.
- Keyset прыгает в нужное место индекса и читает ровно 21 строку на любой глубине.

**SQL-запросов на страницу ленты из 20 событий** (счётчик Hibernate Statistics в тестах):

| Как грузим | Запросов |
|---|---|
| `findAll(Pageable)` и ленивые связи, пачки выключены (`NPlusOneDemoTest`) | больше 30: 1 + count + площадка на событие + артисты на событие |
| JOIN FETCH venue + `default_batch_fetch_size` | **2** |
| Карточка события с `@EntityGraph` | **1** |

**Демо-данные:** 200 000 строк `event_performers` с внешними ключами грузились 42 с, потому что каждая строка проверялась отдельным поиском. С отключёнными на время загрузки ключами и проверкой всей таблицы в `ADD CONSTRAINT` загрузка занимает 1.4 с, весь seed — около 3.5 с вместо 53 с.

## Последствия

- `city` в `events` нужно держать в согласии с `venues.city`. Сейчас площадки не меняют город. Если начнут, понадобится обновление в той же транзакции или триггер.
- Keyset не умеет «перейти на страницу 57»: только вперёд по курсору. Для ленты с бесконечной прокруткой это нормально.
- Связи между базами разных сервисов БД не проверяет: в booking-service у `seats.event_id` больше нет внешнего ключа, событие проверяется вызовом каталога.
- Каталог стал зависимостью брони. Пока он лежит, брони отвечают 503. Circuit breaker и fallback на кэш в блоке 9, общий кэш в Redis в блоке 7а.
- Полнотекстовый поиск (`tsvector`) не делали: поиск с опечатками и фасетами будет в Elasticsearch (блок 7б).
