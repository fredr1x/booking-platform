# ADR 0004: Redis — claim мест, очередь истечения холдов, кэш

**Статус:** принято, 01.11.2026 (блок 7а)

## Контекст

После блоков 3–6 всё держится на PostgreSQL:
- тысяча покупателей одного места — тысяча транзакций, каждая берёт соединение из пула на 20, и 999 из них только для того, чтобы узнать «занято»;
- уборщик холдов раз в 30 секунд сканирует таблицу броней, и бронь истекает с опозданием до 30 секунд (P7);
- цена по спросу на каждую бронь считает статусы всех 20 000 мест события (P8);
- карточка события на каждый запрос читается из БД каталога.

## Решения

### 1. Claim места в Redis до транзакции (режим `REDIS`, по умолчанию)

`SET seat:{eventId}:{seatId} owner NX PX ttl` для каждого места, по возрастанию id. Не поставился ключ → 409 сразу, без соединения с БД. Поставились все → обычная транзакция с атомарным UPDATE из блока 3. Бронь не создалась → поставленные ключи снимаются.

- **Redis — фильтр, а не источник правды.** Место продано, только когда прошёл UPDATE в PostgreSQL и сработал частичный уникальный индекс. Поэтому:
  - ключ истёк раньше брони — запрос дойдёт до БД и получит 409 там;
  - Redis недоступен — claim пропускается с предупреждением в логе, бронь работает как раньше (fail-open).
- **Порядок по id.** Покупатели мест {1, 2} и {2, 1} сталкиваются на первом месте, а не захватывают по одному и не отказывают друг другу оба.
- **Владелец ключа.** Для запроса с Idempotency-Key владелец — `userId:key`, поэтому параллельный дубль проходит Redis и получает ту же бронь из БД, а не 409.
- **Освобождение.** Отмена, отказ оплаты и истечение удаляют ключи сразу. Без этого место было бы недоступно до TTL (холд + 1 минута).

Почему не держать холд **только** в Redis, как планировалось: тогда статус места жил бы в двух системах, а страховочный индекс в БД перестал бы защищать. Полный атомарный холд нескольких мест в Redis (Lua) — в блоке 8а, вместе с виртуальной очередью.

### 2. Очередь истечения холдов: sorted set

`ZADD hold-expirations <expiresAt в мс> <bookingId>` при создании брони. Уборщик раз в секунду:
1. берёт созревшие `ZRANGEBYSCORE 0 now LIMIT 500`;
2. для каждой делает `ZREM` и обрабатывает только те, где удаление вернуло 1. Так несколько инстансов не истекут одну бронь дважды;
3. истекает их в БД, если бронь всё ещё PENDING. Оплаченные и отменённые просто пропускаются, при смене статуса из очереди их не убираем.

Keyspace notifications не используем: Redis не гарантирует их доставку, а событие истечения ключа приходит, когда Redis сам доберётся до ключа.

Старый обход таблицы остался запасным, раз в 5 минут: ловит брони, которых нет в очереди (Redis был недоступен при создании или потерял данные при рестарте).

### 3. Кэш заполненности зала для цены (P8)

`OccupancyService.occupancy(eventId)` под `@Cacheable(sync = true)`, TTL 1 секунда. Цене по спросу секундная неточность не мешает, а на старте продаж тысяча подсчётов в секунду превращается в один на инстанс. `sync = true` — при промахе считает один поток, остальные ждут.

Точные счётчики (`INCR` на каждый холд и освобождение) отложены: их пришлось бы держать в согласии с БД при каждом переходе статуса.

### 4. Кэш карточки события в catalog-service

Cache-aside через `@Cacheable(cacheNames = "events", sync = true)`:
- TTL 10 минут плюс случайные 0–60 секунд: ключи, прогретые одной волной, не истекают одновременно;
- `sync = true` — защита от cache stampede внутри инстанса;
- несуществующее событие не кэшируется: исключение проходит мимо кэша;
- значения сериализуются JSON с конкретным типом `EventResponse`. Обобщённый JSON без информации о типе вернул бы `LinkedHashMap` вместо record и упал бы с `ClassCastException`;
- hit/miss в метрике `cache.gets` (`spring.cache.redis.enable-statistics`).

Инвалидации по Kafka нет: у каталога пока нет API изменения событий. Когда появится, изменение и `@CacheEvict` будут в одном сервисе, а Kafka понадобится для кэшей в других сервисах.

### 5. Redis в compose

`maxmemory 192mb`, `maxmemory-policy volatile-lru`: при нехватке памяти вытесняются только ключи с TTL (claim'ы и кэш), а очередь `hold-expirations` без TTL остаётся. Вытесненный claim не опасен: место защищает БД.

## Замеры

**Тест гонки, 1000 виртуальных потоков, Testcontainers:**

| Режим | Одно место | 1000 разных мест |
|---|---|---|
| ATOMIC | 1 продано, 999 конфликтов, **558 мс** | 2527 мс |
| REDIS | 1 продано, 999 конфликтов, **282 мс** | 2350 мс |

На одном месте вдвое быстрее, потому что 999 проигравших не доходят до БД. На разных местах все запросы честно идут в БД, выигрыша почти нет.

**Вживую через gateway:**
- 50 покупателей одного места: 1 × 201, 49 × 409, все 49 отсеяны в Redis (`booking.seat.claim.rejected` = 49);
- холд 20 секунд: бронь стала EXPIRED через 0.96 с после срока, раньше было до 30 с;
- 20 чтений карточки события: 19 попаданий, 1 промах.

## Последствия

- Claim'ы, очередь и кэш не переживают потерю данных Redis. Корректность от этого не страдает (БД — источник правды, запасной обход таблицы), но после рестарта Redis брони истекают с опозданием до 5 минут.
- Кэш заполненности и карточки свой на ключ, но защита от stampede (`sync`) работает только внутри инстанса: при N инстансах в БД на промахе придут до N запросов.
- Каталог по-прежнему синхронная зависимость брони (P14): кэш снимает нагрузку с БД каталога, но если catalog-service лежит, бронь отвечает 503. Fallback — блок 9.
