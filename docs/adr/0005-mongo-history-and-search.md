# ADR 0005: История броней в MongoDB (CQRS) и поиск событий в Elasticsearch

**Статус:** принято, 06.11.2026 (блок 7б)

## Контекст

- Пользователю нужен список его броней. Если читать его из БД booking-service, запросы истории конкурируют за пул соединений с покупкой билетов, а пул и так рассчитан на пик продаж.
- Каталог умеет только ленту по городу (keyset из блока 5). По названию или артисту ничего не найти, тем более с опечаткой. `LIKE '%...%'` не использует индекс, а `tsvector` в PostgreSQL не исправляет опечатки и нагружает ту же БД.

## Решения

### 1. История броней — read-модель в MongoDB (CQRS)

В notification-service коллекция `booking_history`: один документ на бронь, `_id` = id брони. Документ собирается из событий `booking.events`. `GET /api/v1/users/{id}/bookings` читает только из MongoDB, а gateway направляет этот путь в notification-service.

- **Своя consumer group `booking-history`.** У проекции свой offset, свои повторы и DLT (`-history-retry`, `-history-dlt`). Упавшая проекция не задерживает уведомления. Перестроить её можно, сбросив offset группы, и уведомления при этом не уйдут повторно.
- **Идемпотентность без учёта messageId.** Каждое событие — две записи в MongoDB:
  1. upsert данных брони: сумма, событие, срок, paymentId, причина отмены. Повтор ставит те же значения.
  2. `status` и `statusAt` меняются, только если `statusAt` документа старше события.

  Дубль ничего не меняет. Если событие обогнало предыдущее (то ушло в retry-топик), старое не откатит статус назад. В тесте BookingConfirmed приходит раньше BookingCreated, и итоговый статус — CONFIRMED.
- **Индекс `{userId: 1, createdAt: -1}`.** Фильтр и сортировка по одному индексу.
- **Сумма в Decimal128** (`representation.big-decimal`), а не строкой.
- **Доступ.** Только к своей истории: `X-User-Id` должен совпадать с id в пути, иначе 403. Пока это заголовок, JWT появится в блоке 10.

Цена решения — eventual consistency: история отстаёт от брони на время доставки события (outbox-релей 200 мс + consumer). Сразу после оплаты бронь в истории может быть ещё AWAITING_PAYMENT.

### 2. Поиск событий в Elasticsearch

Индекс `events` в catalog-service: денормализованный документ (название, артисты, площадка, город, даты, статус), без JOIN при поиске. `GET /api/v1/events/search?q=&city=&from=&to=&page=&size=`.

- **Запрос.** `multi_match` по `title^3`, `performers^2`, `venue` с `fuzziness: AUTO`: в словах из 3–5 букв допускается одна опечатка, в более длинных — две, перестановка соседних букв считается одной. Город, даты и `status = ON_SALE` идут в `filter`: на релевантность они не влияют и кэшируются.
- **Маппинг.** `text` — для полнотекстового поиска, `keyword` — для точных фильтров. Один шард и 0 реплик: узел один, с репликой индекс навсегда остался бы yellow.
- **Индекс создаёт код** (`createIndex = false` + `createWithMapping` на старте). Иначе Spring Data проверяет индекс при создании бина, и каталог не стартовал бы без Elasticsearch. Сейчас без Elasticsearch не работает только поиск.
- **Наполнение.** На старте каталог сравнивает число документов в индексе с числом строк в БД. Если документов меньше (индекс пуст или прошлая индексация прервалась), каталог переиндексирует всё: пачки по 1000 через keyset по id, каждая пачка — один bulk-запрос. Документ с тем же id перезаписывается, поэтому повтор безопасен.
- **Пагинация** через `from/size`, страниц не больше 100: `from + size` в Elasticsearch ограничено 10 000 (`max_result_window`).

**Чего нет в плане из ROADMAP:**
- **Синхронизация через Kafka.** У каталога нет API изменения событий, публиковать нечего. Когда API появится, будет outbox `catalog.events` и consumer, обновляющий документ. Сейчас при изменении данных в обход сервиса индекс устареет до следующей полной переиндексации.
- **Русский анализатор, completion-подсказки, фасеты.** Демо-данные на английском, а подсказки и фасеты не нужны ни одному клиенту.

### 3. Elasticsearch в compose

`elasticsearch:9.2.4` (клиент Spring Boot 4.0.8 — 9.2), single-node, без TLS и пароля, куча 512 МБ, `mem_limit 1g`.

## Замеры

| Что | Результат |
|---|---|
| Переиндексация 100 003 событий | 52–57 с |
| Поиск «jaz nigth» через gateway | Jazz Night, медиана 36 мс |
| «flsh sale konsert» | Flash Sale Mega Concert, 38 мс |
| «evnt» + City 5 + январь 2027 | 412 событий, 35 мс |
| История 3 броней через gateway | CONFIRMED / CANCELLED (USER_REQUEST) / PENDING, верные суммы и paymentId |
| Чужая история | 403 |

## Последствия

- Две новые копии данных, которые могут отставать от источника: история (секунды) и поисковый индекс (до перезапуска каталога, если события меняют в обход сервиса).
- Переиндексация на старте добавляет около минуты к первому запуску каталога и к тестам каталога.
- Потеряна MongoDB — история восстанавливается сбросом offset группы `booking-history`, но только пока события лежат в Kafka (retention 7 дней). Полностью восстановить можно только выгрузкой из БД booking-service, её нет.
