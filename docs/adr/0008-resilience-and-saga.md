# ADR 0008: Rate limiter, синхронная оплата с circuit breaker, сага с компенсацией

**Статус:** принято, 15.11.2026 (блок 9)

## Контекст

- Gateway пропускал любой поток запросов (P12). Пропуск из очереди многоразовый (P22): один пользователь мог создать сотни броней.
- Оплата шла через Kafka (ADR 0003). Бронь в `AWAITING_PAYMENT` ждала ответа сколько угодно, отмена во время оплаты оставляла списанные деньги (P16). Circuit breaker на Kafka не имеет смысла: брокер принимает сообщение, даже если платёжка мертва.
- Каталог — синхронная зависимость брони: каталог лежит, бронь отвечает 503 (P14).
- Поиск без Elasticsearch отвечал 500 (P25).

## Решения

### 1. Rate limiter в gateway

`RequestRateLimiter` Spring Cloud Gateway, token bucket в Redis: Lua-скрипт атомарно пополняет бакет по времени и забирает токен. Бакеты общие для всех инстансов gateway.

- Ключ — `X-User-Id`, без него (или со странным id) — IP.
- Общий лимит на все запросы: 50 в секунду, всплеск до 100.
- Отдельный маршрут для `POST /api/v1/bookings/**` (создание, оплата, отмена): 5 в секунду, всплеск до 10. Ключ с префиксом `write:`: RedisRateLimiter хранит бакет по ключу, а не по маршруту, и с одинаковым ключом оба лимита тратили бы один бакет.
- Ответ `429` с `X-RateLimit-Remaining`, а `Retry-After` добавляет свой фильтр (из коробки его нет).
- Redis недоступен — запросы проходят без лимита (fail-open). Лимитер — защита от перегрузки, а не правило бизнеса, и падение Redis не должно ронять весь вход.

Своё скользящее окно на Lua не делали: token bucket из коробки закрывает задачу, разница в точности на границе окна здесь не важна.

**Ограничение:** `X-User-Id` не проверяется (аутентификации нет), меняя id, клиент обходит лимит. С JWT ключом станет subject токена.

### 2. Оплата — синхронный REST

payment-service получил API: `POST /api/v1/payments` (authorize, id платежа в `Idempotency-Key`) и `POST /api/v1/payments/{id}/refund`. Kafka из payment-service убрана, топик `payment.events` и таблица `processed_messages` больше не нужны. Событие `PaymentRequested` в `booking.events` осталось: по нему notification-service строит историю.

Идемпотентность по `paymentId`: результат пишется `INSERT ... ON CONFLICT DO NOTHING`, первый выигрывает. Refund неизвестного платежа пишет строку `VOIDED`. Если authorize дошёл позже (booking-service уже не дождался и отменил), он увидит `VOIDED` и деньги не спишет.

### 3. Resilience4j на вызове платёжки

Core-модули Resilience4j без Spring-стартера: совместимость стартера с Spring Boot 4 не гарантирована, а программная сборка — десяток строк. Порядок снаружи внутрь: retry → circuit breaker → bulkhead → HTTP.

| Механизм | Настройка | Зачем |
|---|---|---|
| Таймаут | 2 с на попытку | обычный ответ 0.5 с; дольше ждать — держать поток ради почти наверняка мёртвой платёжки |
| Retry | 2 попытки, пауза 200 мс, только таймаут, обрыв и 5xx | безопасен: тот же `Idempotency-Key`, второго списания не будет |
| Circuit breaker | 50% сбоев среди последних 10 вызовов (минимум 5), открыт 10 с, 2 пробных вызова | при мёртвой платёжке сразу отказ, не тратя 4 с на попытки; платёжка получает паузу |
| Bulkhead | 20 одновременных вызовов, без ожидания | медленная платёжка не забирает все потоки сервиса |

Пока breaker открыт, `POST /bookings/{id}/pay` сразу отвечает `503` с `Retry-After`, а бронь не трогается: клиент повторит оплату позже, места остаются за ним до конца холда.

### 4. Сага с оркестратором

Оркестратор `PaymentSagaService` в booking-service, состояние в таблице `saga_state` (одна строка на бронь). Шаги: места захолжены (при создании брони) → авторизация → подтверждение.

```
AUTHORIZING ──успех──► COMPLETED (бронь CONFIRMED)
     │
     ├──отказ банка──► COMPENSATED (бронь CANCELLED, места свободны, возвращать нечего)
     │
     └──таймаут / 5xx / breaker / бронь отменили во время оплаты
                  ──► COMPENSATING (бронь CANCELLED, места свободны) ──refund──► COMPENSATED
```

- Локальные шаги — короткие транзакции. Вызов платёжки идёт между ними, без открытой транзакции: соединение из пула на 20 на время HTTP не держится.
- Шаг пишется в `saga_state` до вызова. Переход только из ожидаемого шага, под `SELECT ... FOR UPDATE`: запрос и уборщик не продвинут сагу дважды.
- Компенсация в обратном порядке. Освобождение мест локальное и не может не пройти, поэтому делается сразу вместе с отменой брони: место возвращается в продажу, не дожидаясь платёжки. Возврат денег удалённый: не прошёл — сага остаётся в `COMPENSATING`.
- Уборщик (`SagaRecoveryScheduler`, раз в 5 с) повторяет возврат для `COMPENSATING` старше 10 с. Саги в `AUTHORIZING` старше минуты (сервис упал посреди вызова) он доводит повторным authorize: тот идемпотентен и вернёт результат, если платёж прошёл до падения.
- Отмена пользователем во время оплаты: authorize вернул успех, а бронь уже `CANCELLED` — сага идёт в компенсацию и возвращает деньги (закрывает вторую половину P16).

Новая причина отмены `PAYMENT_UNAVAILABLE`: платёжка не ответила.

### 5. Каталог: circuit breaker и fallback в Redis

Каждый успешный ответ каталога пишется в Redis (`catalog-event:{id}`, 10 минут). Каталог не ответил или его breaker открыт (50% сбоев из последних 20) — бронь берёт последнее известное событие. «Событие не найдено» сбоем не считается. Ошибки Redis глушатся: это запасной путь.

**Ограничение:** в fallback статус события может отстать до 10 минут: продажу закрыли, а бронь ещё проходит.

### 6. Поиск без Elasticsearch — 503

`DataAccessResourceFailureException` (ES или БД недоступны) в каталоге теперь `503` с `Retry-After: 5`, а не 500.

## Замеры

k6 `load/payment-chaos.js`, 60 с: 10 покупателей в секунду бронируют и платят, 100 читателей в секунду читают карточку события и заполненность зала. payment-service с `PAYMENT_ERROR_RATE=0.5 PAYMENT_DELAY=3s`: каждый ответ через 3 с, половина из них 500. Всё на одном ноутбуке, сервисы прогреты.

| | С защитой | Без защиты |
|---|---|---|
| Настройки | по умолчанию | таймаут 10 с, 1 попытка, breaker не открывается, bulkhead 1000 |
| Оплата, медиана | **7 мс** | 3.11 с |
| Оплата, p99 | 4.34 с | 3.43 с |
| Быстрых отказов 503 | 289 | 0 |
| Вызовов платёжки (саг) | 9 | 28 |
| Оплачено | 0 | 12 |
| Карточка события, p99 | 32 мс | 30 мс |
| Заполненность зала, p99 | 92 мс | 79 мс |
| Создание брони, p99 | 1.17 с | 0.77 с |
| Броней в `AWAITING_PAYMENT` после прогона | 0 | 0 |

После прогона с защитой 2 саги ждали возврата в `COMPENSATING`, через 20 с уборщик довёл все 9 до `COMPENSATED`.

**Выводы:**

- **Breaker экономит время пользователя и платёжку, а не остальную систему.** С защитой оплата отвечает за 7 мс вместо 3 с, а платёжка получила втрое меньше вызовов, пока ей плохо. p99 4.34 с — первые саги до открытия breaker'а: две попытки по 2 с.
- **Чтение не пострадало ни в одном варианте.** Ожидание платёжки держит виртуальный поток, а не поток ОС, и соединение с БД на время HTTP не берётся. Защиту остальной системы дала архитектура (блоки 1 и 3), а не breaker.
- **Цена breaker'а:** пока он открыт, отказ получают и те оплаты, которые прошли бы (половина ответов платёжки успешна). Без защиты оплачено 12 броней, с защитой ни одной. Это осознанный обмен: быстрый отказ вместо 3 с ожидания с шансом 50%.
- Первый прогон с защитой шёл на холодных сервисах, и каталог параллельно индексировал 100 000 событий: p99 карточки события был 2.5 с. Сравнивать можно только прогретые прогоны.

Живая проверка rate limiter'а: 429 с `X-RateLimit-Remaining: 0` и `Retry-After: 1`. Всплеск проверяет интеграционный тест `RateLimitIntegrationTest` с Redis в Testcontainers.

## Последствия

- Оплата — синхронный вызов: при медленной платёжке пользователь ждёт до 4 с, а не уходит сразу с `AWAITING_PAYMENT`.
- `RequestIdFilterTest` поднимает gateway без Redis: лимитер работает fail-open, в логе ошибки подключения.
- Параметры breaker'а (окно 10, порог 50%) подобраны на глаз, проверка под реальной нагрузкой — блок 11.
- Состояние breaker'ов видно только в логе. Метрики и дашборд — блок 10.
